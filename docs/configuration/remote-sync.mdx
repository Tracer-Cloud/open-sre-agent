---
title: "Sync to your own object store"
description: "Copy sessions and memory between machines using an S3, GCS, Azure, or Vercel Blob store you own."
---

By default OpenSRE keeps everything on your machine. Turn on remote sync to copy **conversations** and **memory** to a private store you own, so another laptop can continue where you left off.

Credentials and API keys stay local. You still run integration setup on each new machine.

| Copied | Not copied |
| --- | --- |
| `~/.opensre/sessions/` | Integration credentials |
| `~/.opensre/memory/` | Model API keys |

<Warning>
Use a **private** store. Unless you turn on [encryption](#encryption), it holds incident chats and system details in readable form.
</Warning>

## Setup

```bash
# Interactive (writes ~/.opensre/config.yml)
opensre remote-sync setup

# AWS / S3
opensre remote-sync setup --provider aws --bucket my-opensre-bucket

# Google Cloud Storage (Application Default Credentials)
opensre remote-sync setup --provider gcs --bucket my-opensre-bucket

# Vercel Blob
opensre remote-sync setup --provider vercel --bucket opensre-remote-sync
export BLOB_READ_WRITE_TOKEN=vercel_blob_rw_...

# Azure Blob (ambient Azure credentials)
opensre remote-sync setup --provider azure --bucket my-container
```

Same flags work as `/remote-sync setup` in the interactive shell. On chat gateways, pass flags (no interactive prompts) — or use the CLI.

Or set env vars yourself:

```bash
export OPENSRE_REMOTE_SYNC=1
export OPENSRE_REMOTE_SYNC_BUCKET=my-opensre-bucket
# optional:
# export OPENSRE_REMOTE_SYNC_PROVIDER=aws   # default; also gcs, vercel, azure
# export OPENSRE_REMOTE_SYNC_PREFIX=opensre # default
```

A bucket name alone does nothing — you must also set `OPENSRE_REMOTE_SYNC=1` (or enable it via `opensre remote-sync setup`).

| Variable | What it does |
| --- | --- |
| `OPENSRE_REMOTE_SYNC` | `1` / `true` turns sync on |
| `OPENSRE_REMOTE_SYNC_PROVIDER` | `aws` (default), `gcs`, `vercel`, `azure`, or `s3compat` |
| `OPENSRE_REMOTE_SYNC_BUCKET` | Bucket, container, or Blob store name (required when on) |
| `OPENSRE_REMOTE_SYNC_PREFIX` | Key prefix (default `opensre`). Same prefix = shared history |
| `OPENSRE_REMOTE_SYNC_REGION` | AWS region (AWS only) |
| `OPENSRE_REMOTE_SYNC_PROFILE` | AWS profile name, or Azure storage account name when `provider=azure` |
| `OPENSRE_REMOTE_SYNC_ENDPOINT_URL` | Custom S3 endpoint when `provider=s3compat` (MinIO / R2 / Spaces) |
| `BLOB_READ_WRITE_TOKEN` | Vercel Blob token (Vercel only) |
| `OPENSRE_REMOTE_SYNC_EXCLUDE` | Comma-separated paths to skip (see below) |
| `OPENSRE_REMOTE_SYNC_EXCLUDE_OFF` | `1` ignores exclusions for one run |
| `OPENSRE_REMOTE_SYNC_ENCRYPT` | `1` seals contents before upload (see [Encryption](#encryption)) |
| `OPENSRE_REMOTE_SYNC_PASSPHRASE` | Passphrase the contents are sealed under |

Env vars override `~/.opensre/config.yml` for that run. `--region` / `--profile` only work with AWS and Azure (profile = storage account); setup rejects them for other providers.

Every machine that should share history needs the **same provider, store, and prefix** (and for Vercel, a token for that store) — plus the same passphrase when encryption is on.

## Encryption

Without it, whoever runs the store can read your sessions and memory. Turn it on and contents are sealed on your machine first, under a key derived from a passphrase only you hold. `setup` asks:

```bash
opensre remote-sync setup
# Encrypt contents [y/N]: y
# Encryption passphrase: *********
```

Pass `--encrypt` or `--no-encrypt` to answer up front. A run with no terminal is never asked and defaults to off — for unattended setup, pass `--encrypt` and set `OPENSRE_REMOTE_SYNC_PASSPHRASE`.

<Warning>
Lose the passphrase and the store's contents are unrecoverable. There is no reset and no copy of the key anywhere else.
</Warning>

On another machine, set the same passphrase; the salt and wrapped key come from the store. It resolves from `OPENSRE_REMOTE_SYNC_PASSPHRASE`, else `~/.opensre/credentials.json` (owner-only, and not itself encrypted — it guards the *remote* store). `OPENSRE_DISABLE_KEYRING=1` makes the env var the only source.

```bash
opensre remote-sync rotate-passphrase   # re-wraps the key; no object re-uploaded;
opensre remote-sync reencrypt           # re-encrypts whole data and encrypts already stored readable data on cloud.
```

If `OPENSRE_REMOTE_SYNC_PASSPHRASE` is exported, update that export after rotating, as it outranks `~/.opensre/credentials.json` — a stale one shadows the rotation even on the machine that ran it. 
With `OPENSRE_DISABLE_KEYRING=1`, the export is the only place it can go.

`reencrypt` re-uploads everything and overwrites each object in place. On a **versioned** bucket the old readable versions survive — remove noncurrent versions yourself.

<Warning>
The store prefix must be dedicated to OpenSRE — `reencrypt` processes every object it finds there. If anything else shares the prefix, it will be overwritten with an encrypted copy that only OpenSRE can read.
</Warning>

<Warning>
The first encrypted sync from a machine, `rotate-passphrase`, and `reencrypt` are not safe to run concurrently — not at the same time as each other, and not from two machines at once.
Each one writes the manifest, so the last write wins and can leave objects the other machine uploaded undecryptable.

Set encryption up on one machine and let its first sync finish before starting a second machine; before a rotation or reencrypt, make sure no other rotation, reencrypt, or first sync is running.
</Warning>

Encryption fails closed. A sync is refused, never downgraded, when:

- no passphrase is available, or it is wrong
- the store already holds unencrypted objects (run `reencrypt`)
- the store is encrypted but encryption is off on this machine
- a stored object cannot be decrypted — your local file is left untouched

`opensre remote-sync status` reports all of these before you sync.

### What encryption assumes

Encryption assumes the store can be **read** but not **written** by someone you don't trust. Whoever runs the store, holds a copy of the bucket, or reads it later sees only sealed bytes. That is the case it closes.

**Not hidden:** object keys (session ids, memory filenames), object sizes (+49 bytes), and timestamps. Those sessions were also sent to your model provider — this keeps history out of third-party storage, it is not end-to-end confidentiality.

**Out of scope:** Anyone who can **write** to the store, can corrupt it. Encryption stops them reading your history; it does not stop them wrecking the manifest — the small key record OpenSRE keeps in the store, which holds the encrypted root keys.

If it gets corrupted, sync may refuse in both directions and content may get sealed against an unintended key — even if your passphrase remains intact — though it leaves your local files untouched.
Your own machines still hold the originals, so recovery is restoring the manifest from a bucket version, or emptying the prefix and syncing again from a machine that still has the files.

A leaked passphrase needs `rotate-passphrase` and `reencrypt`. Only `rotate-passphrase` re-wraps the same content keys, so whoever kept a copy of the old key record and knows the old passphrase can still read every object — including ones uploaded after the rotation. 
`reencrypt` starts a new key generation and re-seals everything under it.

Even that is not post-compromise recovery: it cannot take write access away from whoever already had it. Revoke the store credentials that leaked alongside the passphrase, 
and if you cannot be sure they are revoked, sync to a **new bucket or prefix** and treat the old one as exposed.

Closing the write side is a control on your store, not something OpenSRE can enforce: S3 Object Lock, versioning with a deny-overwrite policy, or write credentials scoped to machines you trust. These differ per provider, and OpenSRE never requires them.

## Sync

```bash
opensre remote-sync status          # what would move
opensre remote-sync sync            # pull, then push
opensre remote-sync sync --pull-only   # new machine: download only
opensre remote-sync sync --push-only   # upload only
```

In the shell: `/remote-sync status` and `/remote-sync sync`.

To run one full sync automatically after an interactive shell session exits:

```bash
opensre --sync-on-exit
```

Run setup first. The flag applies only to that invocation; a normal `opensre`
session remains manual-only. If the automatic sync fails, OpenSRE prints a
warning without changing the shell's exit status.

<Warning>
Remote sync is for a **personal machine**. Org-bound Slack/Discord turns are refused — those already persist under the org context root.
</Warning>

## Providers

**AWS / S3** — private bucket. Uses your normal AWS credentials (`AWS_*`, profile, or SSO). Uploads use server-side encryption (`AES256`). Needs `s3:ListBucket`, `s3:GetObject`, and `s3:PutObject` on your prefix. Sync never deletes objects, so `s3:DeleteObject` is not required.

**Google Cloud Storage** — private bucket. Set `OPENSRE_REMOTE_SYNC_PROVIDER=gcs`. Credentials come from Application Default Credentials (`gcloud auth application-default login`). Needs `storage.objects.list`, `storage.objects.get`, `storage.objects.create`, and `storage.objects.delete` (delete is required to replace an object even though sync never removes keys). A bucket-scoped `roles/storage.objectUser` binding covers all four.

**Vercel Blob** — private store. Set `BLOB_READ_WRITE_TOKEN`. `OPENSRE_REMOTE_SYNC_BUCKET` is the store name/id for status.

**Azure Blob Storage** — private container. Set `OPENSRE_REMOTE_SYNC_PROVIDER=azure`, `OPENSRE_REMOTE_SYNC_BUCKET` to the container name, and `OPENSRE_REMOTE_SYNC_PROFILE` to the storage account name. Auth uses ambient Azure credentials (`az login`, Managed Identity, or `AZURE_*`). The principal needs **Storage Blob Data Contributor** on the account (plain Contributor is not enough).

**S3-compatible (MinIO / R2 / Spaces)** — set `OPENSRE_REMOTE_SYNC_PROVIDER=s3compat` and `OPENSRE_REMOTE_SYNC_ENDPOINT_URL` to the custom endpoint (or `AWS_ENDPOINT_URL_S3`). Path-style addressing is enabled for MinIO. Use the same ambient S3 credentials as AWS.

## Skip some paths

By default every session and memory file syncs. To hold some back:

```bash
export OPENSRE_REMOTE_SYNC_EXCLUDE='*.tmp,sessions/scratch-*'
```

Or in `~/.opensre/config.yml`:

```yaml
remote_sync:
  enabled: true
  bucket: my-opensre-bucket
  exclude:
    - "*.tmp"
    - sessions/scratch-*
```

If the env var is set, it **replaces** the config list for that run (it does not merge). Clearing the env var to empty does **not** turn exclusions off — use this instead:

```bash
OPENSRE_REMOTE_SYNC_EXCLUDE_OFF=1 opensre remote-sync sync
```

Patterns match keys like `sessions/…` or `memory/…` (case-sensitive). `*` can cross folders. Excluded paths are skipped both ways (not uploaded, not downloaded). Patterns starting with `!` are rejected. Sync never deletes from the store.

## Conflicts

Sync pulls first, then pushes.

- Only on one side → copied to the other
- Both changed → newer write wins
- Nothing is deleted on either side

Deleting a session on one laptop does **not** remove it from the store or other machines. Delete the object in the store if you want it gone everywhere.
