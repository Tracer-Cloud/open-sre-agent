---
title: "Mattermost"
description: "Deliver investigation findings to a Mattermost channel."
---

OpenSRE's Mattermost integration delivers investigation findings to any channel your user or bot account can post to — useful for teams running self-hosted or cloud Mattermost workspaces.

Start the interactive shell with `opensre` (no subcommand). Slash commands below are run from that REPL.

<Note>
Mattermost support is **outbound delivery only** (investigation reports posted to a channel). Triggering investigations from Mattermost chat is not supported yet.
</Note>

---

## Prerequisites

- A Mattermost workspace (self-hosted or cloud) and its base URL, e.g. `https://chat.example.com`.
- An account allowed to post in the destination channel. A dedicated bot account is recommended so findings are not attributed to a personal user.
- The **Personal Access Tokens** feature enabled on the server (`System Console → Integrations → Integration Management → Enable Personal Access Tokens`) — or admin access to create an **incoming webhook**.

---

## Pick a mode

| Mode | Credentials | Destination | Best for |
|---|---|---|---|
| **Personal Access Token** (recommended) | `server_url` + `auth_token` | Any channel, chosen per message by channel id | Dynamic channel targeting, verifiable via `/api/v4/users/me` |
| **Incoming webhook** | single `webhook_url` | Fixed channel chosen when the webhook is created | Simplest setup; no bot account needed |

You can configure both — when both are present, delivery prefers the webhook.

---

## Step 1 (token mode): Create a Personal Access Token

1. Sign in to Mattermost with the account that should post findings.
2. Open **Settings → Security → Personal Access Tokens**.
3. Select **Create Token**, enter a description (e.g. `opensre`), and confirm.
4. Mattermost shows the **token** once. Copy it — it is your `auth_token`. Treat it like a password.

Unlike Rocket.Chat, Mattermost's REST API authenticates with the token alone (`Authorization: Bearer <token>`) — there is no separate user-id header to copy.

---

## Step 1 (webhook mode): Create an incoming webhook

1. As an admin, open **System Console → Integrations → Incoming Webhooks → Add Incoming Webhook**.
2. Set a display name (e.g. `opensre`) and pick the destination **channel**.
3. Select **Save**. Mattermost shows the **Webhook URL** (`https://<server>/hooks/<id>`). Copy it — the token is embedded in the URL, so treat the whole URL like a password.

---

## Step 2 (token mode): Find the destination channel id

Findings are posted with the `POST /api/v4/posts` REST endpoint, which — unlike Rocket.Chat's `chat.postMessage` — requires the channel's **id**, not its display name or `~handle`.

The fastest way to find it: open the channel in Mattermost, click the channel name to open **View Info**, and copy the **Channel ID** shown there (also visible in the URL of most admin/API views). Make sure the token's account is a member of the channel (or has permission to post there).

---

## Step 3: Configure the integration

### Option A: Onboarding wizard (recommended)

Interactive shell:

```text
/onboard
```

CLI:

```bash
opensre onboard
```

Choose **Mattermost** from the integration list, then pick **token**, **webhook**, or **both**. The wizard prompts for:

- Token mode: **Server URL** (`MATTERMOST_SERVER_URL`), **personal access token** (OS keyring via `sync_env_secret`, not plain `.env`), and **default channel** (`MATTERMOST_DEFAULT_CHANNEL`, a channel id)
- Webhook mode: **webhook URL** — saved to the integration store (`~/.opensre/integrations.json`) and/or `MATTERMOST_WEBHOOK_URL` in `.env`; never written to the keyring (`*_URL` is non-keyring config). The URL often embeds a token — treat it like a password for logging/masking.

Credentials are also saved to `~/.opensre/integrations.json` via `upsert_integration("mattermost", ...)`.

### Option B: Environment variables

Set in `.env` (PAT can also live in the keyring after wizard setup):

```bash
# Token mode
MATTERMOST_SERVER_URL=https://chat.example.com
MATTERMOST_AUTH_TOKEN=<personal-access-token>
MATTERMOST_DEFAULT_CHANNEL=<channel-id>

# Webhook mode (either mode alone is enough; both may be set)
MATTERMOST_WEBHOOK_URL=https://chat.example.com/hooks/<id>
```

| Variable | Description |
|---|---|
| `MATTERMOST_SERVER_URL` | Base URL of your Mattermost server. Required for token mode. |
| `MATTERMOST_AUTH_TOKEN` | Personal access token. Required for token mode. Resolved via env then keyring. |
| `MATTERMOST_DEFAULT_CHANNEL` | Default delivery destination — a Mattermost channel **id**, not its name. Required for token-mode delivery. |
| `MATTERMOST_WEBHOOK_URL` | Incoming webhook URL. Store/env only — never keyring (still treat like a password when logging). Enables webhook mode on its own; preferred over token mode when both are set. |

OpenSRE picks these up at startup and registers Mattermost as an active integration.

<Note>
**Credential resolution.** Token mode: store → `resolve_env_credential("MATTERMOST_AUTH_TOKEN")` (env then keyring). Webhook mode: store → plain `MATTERMOST_WEBHOOK_URL` env — never keyring. Server URL and default channel stay plain env / store.
</Note>

## Step 4: Verify

Interactive shell:

```text
/integrations verify mattermost
```

Or:

```text
/verify mattermost
```

CLI:

```bash
opensre integrations verify mattermost
```

With token credentials configured, this calls Mattermost's [`/api/v4/users/me`](https://api.mattermost.com/#tag/users/operation/GetUser) endpoint and reports the authenticated `@username`. With webhook-only configuration, it runs a **non-posting reachability probe** against the webhook URL (a 404 means the URL or its embedded token is wrong; no message is delivered by the probe).

You can also trigger a real delivery test against a bundled fixture:

Interactive shell:

```text
/investigate tests/e2e/kubernetes/fixtures/datadog_k8s_alert.json
```

CLI:

```bash
opensre investigate --input tests/e2e/kubernetes/fixtures/datadog_k8s_alert.json
```

Findings should appear in the configured channel as a message with an attachment titled **Investigation Complete**. Long reports are truncated to 4,096 characters.

## Programmatic messaging: `mattermost_send_message` tool

When the Mattermost integration is configured, OpenSRE exposes a
`mattermost_send_message` tool. The tool can send user-requested action
messages, incident notifications, or follow-up updates to the configured
default channel, or to an explicit `channel` (channel id) when one is
supplied. Ask in plain language from the interactive shell (for example:
"send a Mattermost message to the team that DB CPU is back below 70%").

```json
{
  "name": "mattermost_send_message",
  "arguments": {
    "channel": "<channel-id>",
    "message": "DB CPU is back below 70%; keeping the incident open for 10 minutes."
  }
}
```

The tool resolves credentials internally from the integration store, then the
same env/keyring rules as setup (PAT via `resolve_env_credential`; webhook URL
via plain env) — the agent never sees them. In token mode an explicit `channel`
(or the configured `default_channel`) is targeted via `POST /api/v4/posts`; in
webhook-only mode messages go to the webhook's fixed destination, and an
explicit `channel` returns a configuration error instead of being silently
ignored.

Delivery is an external side effect and requires approval. The result includes
a stable `status`, `sent`, `error_type`, `channel`, and `message_length` shape
so follow-up tool calls can tell configuration failures from Mattermost
delivery failures.

## Background RCA completion notifications

When the interactive shell runs investigations in background mode, Mattermost can deliver the RCA summary as soon as a job finishes. Configure the integration first, then in the shell:

```text
/background on
/background notify set mattermost          # or: email,mattermost
/investigate datadog
```

On completion the summary — root cause, top analysis, next steps, and a short stats block — is posted as plain text, capped at 4,096 characters. Token mode posts to the configured `default_channel`; webhook-only setups deliver to the webhook's fixed destination.

Confirm delivery with `/background show <task_id>`: the `notify` row reads `mattermost:sent`, `mattermost:failed: <error>`, or `mattermost:missing mattermost integration: …` when neither token credentials (with a default channel) nor a webhook is configured. A notification problem never fails the investigation itself.

See [Background investigations](/background-investigations) for the full command set.

## Watchdog alarms

The process watchdog (`/watch`, `opensre watchdog`) can send threshold alarms to Mattermost instead of Telegram:

```text
/watch <pid> --max-cpu 80 --provider mattermost --chat-id "<channel-id>"
```

CLI:

```bash
opensre watchdog --pid <pid> --max-cpu 80 --provider mattermost --chat-id "<channel-id>"
```

`--chat-id` overrides the configured `default_channel` (token mode) or is optional in webhook-only mode (the webhook's destination is fixed). Alarms require token credentials with a resolvable channel, or a configured incoming webhook — the same rule as scheduled deliveries. Cooldown suppresses repeat alarms for the same threshold (`--cooldown`, default 5 minutes).

## Scheduled deliveries (cron)

With token credentials configured (Steps 1–4), Mattermost can receive recurring reports:

Interactive shell:

```text
/cron add --kind daily_summary --cron "0 9 * * 1-5" --tz America/Sao_Paulo --provider mattermost --chat-id "<channel-id>"
```

CLI:

```bash
opensre cron add --kind daily_summary --cron "0 9 * * 1-5" \
  --tz America/Sao_Paulo --provider mattermost --chat-id "<channel-id>"
```

`--chat-id` is the Mattermost destination channel id. Scheduled deliveries always target that explicit destination, so they require **token credentials** — an incoming webhook's destination is fixed at creation time and cannot honor `--chat-id`. See [Cron](/cron) for task kinds and scheduler daemon setup.

## Troubleshooting

`/integrations verify mattermost` only calls `/api/v4/users/me`, so it surfaces credential errors but cannot detect channel-routing problems. Delivery-time errors only show up when an investigation actually posts; they appear in OpenSRE logs as `[mattermost] post message failed: <error>`.

**`Mattermost auth failed: auth_token is invalid or expired.`**

The token was revoked. Regenerate it under **Settings → Security → Personal Access Tokens** and update `MATTERMOST_AUTH_TOKEN`.

**`channel_id does not exist` / 404 or 403 on post (delivery-time)**

The id in `MATTERMOST_DEFAULT_CHANNEL` is wrong, or the token's account cannot see that channel. Confirm you copied the channel **id** (not its name) and that the account is a member.

**`Mattermost API check failed: <connection error>`**

`MATTERMOST_SERVER_URL` is wrong or unreachable from the machine running OpenSRE. Confirm the URL opens in a browser and includes the scheme (`https://`).

**`Mattermost webhook returned 404; the URL looks invalid.`**

The webhook was deleted, disabled, or the URL was copied incompletely. Open **System Console → Integrations → Incoming Webhooks**, confirm it is enabled, and copy the full URL again.

**Findings never arrive, but `verify` passes**

`/api/v4/users/me` only confirms token credentials and the webhook probe only confirms reachability; neither tests a real delivery. In token mode, confirm `MATTERMOST_DEFAULT_CHANNEL` is set — without it (and without a webhook), delivery is silently skipped (logged as `mattermost delivery: skipped`). In webhook mode, confirm the webhook is enabled and posts to the channel you expect.
